# Приложение контроля касок на Firefly

Приложение `firefly_app` объединяет захват видео, RKNN FP16, прямоугольную зону
контроля, временное подтверждение тревоги, периферию, журнал SQLite и веб-панель.
На плате не нужны PyTorch, Ultralytics и инструменты обучения.

## Быстрый запуск демо на Windows

Из корня клонированного репозитория, в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r firefly_app/requirements.txt
.\.venv\Scripts\python.exe -m firefly_app --demo
```

Откройте <http://127.0.0.1:8080>. Демо не требует модели, камеры или RKNNLite.
Кадры и детекции синтетические; GPIO и UART в этом режиме запрещены.
Цикл длится 40 секунд:

| Время | Сцена | Ожидаемое состояние с исходными настройками |
|---|---|---|
| 0–6 с | Голова без каски вне зоны | SAFE |
| 6–14 с | Голова без каски в зоне | PENDING → ALARM |
| 14–22 с | Каска в зоне | ALARM → SAFE |
| 22–28 с | Пустая сцена | SAFE |
| 28–32 с | Отключение камеры | FAULT |
| 32–40 с | Восстановление камеры, голова без каски в зоне | PENDING → ALARM |

Демо проверяет приложение и сценарий презентации, но не качество детектора.

## Запуск на Firefly

Требуются Python 3.10, RKNNLite/Runtime 2.3.2 и готовая **FP16** модель.
Веса `.rknn` не входят в Git: возьмите проверенный артефакт команды или соберите
его по разделу «RKNN на Firefly» в README. `download_model.py` загружает PT,
а не RKNN. По умолчанию приложение проверяет SHA-256 FP16-артефакта из
`reports/rknn_conversion.md`; известные экспериментальные INT8 не пройдут проверку.

На плате можно клонировать существующее рабочее окружение команды:

```bash
conda create -n helmet-edge --clone 24942
conda activate helmet-edge
python -m pip install -r firefly_app/requirements.txt
python -c 'import cv2, numpy; from rknnlite.api import RKNNLite; print("runtime imports OK")'
python -m firefly_app --source 0 --model models/helmet_detector_fp16.rknn
```

`--source 0` означает первую USB UVC-камеру. Можно передать `/dev/videoN`,
видеофайл или RTSP URL. Физически неподключённый CSI-сенсор не исправляется этим
приложением. При ошибке чтения камера освобождается и переподключается через
секунду. Обычный файл считается записью: он воспроизводится с собственной
частотой кадров и по достижении конца перематывается, не переходя в FAULT. Если
запись не читается вовсе, это по-прежнему ошибка источника. Подробнее — в разделе
«Проверка на записи вместо камеры».

Если модель отсутствует, хеш не совпал или RKNNLite не загрузился, панель
покажет FAULT с причиной. Исправьте причину и перезапустите приложение.
Новый проверенный FP16-артефакт можно принять через `--expected-sha256 HASH`;
не используйте этот параметр для обхода проверки экспериментального INT8.

Панель по умолчанию слушает только localhost. Для доступа с ноутбука:

```bash
ssh -L 8080:127.0.0.1:8080 firefly@100.107.247.216
```

Затем откройте <http://127.0.0.1:8080> на ноутбуке. Панель не имеет встроенных
учётных записей; SSH обеспечивает доступ. `--host 0.0.0.0` предназначен только
для доверенной изолированной сети, где всем клиентам разрешён просмотр камеры
и изменение настроек.

## Зона и подтверждение

Протяните прямоугольник на видео и нажмите «Сохранить». Кнопка «Весь кадр»
подготавливает зону на весь кадр; изменение тоже требует сохранения.
ROI задаётся нормированными координатами `[left, top, right, bottom]`.
Принадлежность определяется **центром бокса головы/каски**, а не ногами человека.
Серые боксы находятся вне зоны. Их наличие не вызывает тревогу.

- SAFE: подтверждённых нарушений нет; отсутствие детекций также даёт SAFE.
- PENDING: `no_helmet` внутри зоны ожидает подтверждения.
- ALARM: нарушение сохраняется не менее `alarm_on_seconds`.
- FAULT: потеря/зависание камеры, устаревший результат, ошибка модели или периферии.

Таймеры используют монотонное время. Переходы по детекциям выполняются только
при получении **нового** результата; повторное чтение одного кадра не подтверждает
тревогу. FAULT сбрасывает подтверждение, после восстановления оно начинается заново.
Для снятия ALARM нужна непрерывная серия результатов без нарушения длительностью
`alarm_off_seconds`. Любой `no_helmet` в зоне удерживает общую тревогу при нескольких
людях. Трекинг и индивидуальные события для каждого человека пока не реализованы.

Исходные настройки — `configs/firefly.json`. Панель сохраняет изменения в
`runtime/settings.json`; они переживают перезапуск и имеют приоритет над исходным
файлом. `--data-dir` выбирает другое хранилище. При сохранении настроек текущий
эпизод закрывается и подтверждение начинается заново.

## LED и ESP32

Выходы отключены, если параметры не переданы. Для LED:

```bash
python -m firefly_app --source 0 --led /sys/class/leds/:user/brightness
```

Путь должен быть доступен пользователю на запись. Не запускайте всё приложение
от root ради LED; настройте права на нужный узел на стенде. ALARM зажигает LED,
FAULT мигает им, SAFE/PENDING выключают.

Для ESP32:

```bash
python -m firefly_app --source 0 --uart /dev/ttyS7 --max-sound-seconds 10
```

`pyserial` входит в runtime requirements. Протокол UART, 115200 8N1:

```text
ALARM:1\n
FAULT:0\n
```

Приложение повторяет состояние раз в секунду. В FAULT отправляется `ALARM:0`
и `FAULT:1`. При штатном завершении выходы выключаются. Звук ограничен временем
`--max-sound-seconds` и не запускается повторно до следующего эпизода ALARM;
LED остаётся включённым до снятия тревоги.

Пример прошивки — `esp32/helmet_alarm/helmet_alarm.ino`. Перед загрузкой
сверьте GPIO с конкретной платой. Пример использует RX16/TX17, LED2, активный
буззер через транзистор/MOSFET на GPIO25. Соедините общий GND и используйте
совместимые уровни UART. Прошивка выключает звук и мигает LED при отсутствии
команд более трёх секунд; независимое ограничение звука — 10 секунд.
Прошивка не собрана и не проверена на физической ESP32.

После принудительного убийства процесса невозможно гарантировать сброс sysfs LED;
аппаратный watchdog ESP32 нужен для реакции на такой сбой. Зависший вызов камеры
или NPU обнаруживается отдельным supervisor по возрасту кадров/результатов.
Если нативный вызов не возвращается, перезапустите процесс после устранения причины.

## Проверка на записи вместо камеры

Пока на стенде нет рабочего сенсора, весь тракт проверяется на записи: `--source`
принимает путь к файлу. Файл воспроизводится с собственной частотой кадров и по
достижении конца перематывается без перехода в FAULT, поэтому таймеры
подтверждения видят нарушение столько времени, сколько оно длится в записи.
Символьные устройства вида `/dev/video0` и сетевые потоки остаются живыми
источниками и читаются как раньше.

Сценарный клип собирается из тестовой части датасета:

```bash
python scripts/make_test_clip.py --overwrite
```

Скрипт отбирает кадры по тому, попадает ли центр бокса в ROI из
`configs/firefly.json`, и склеивает три сегмента: безопасный, с нарушением и
снова безопасный — каждый длиннее соответствующего порога подтверждения. Рядом с
клипом пишется `test_clip.json` с SHA-256, таймлайном и перечнем кадров.

Ожидаемая последовательность при штатных настройках: `SAFE`, затем `PENDING` и
через `alarm_on_seconds` — `ALARM`, затем на безопасном сегменте `ALARM`
удерживается `alarm_off_seconds` и сменяется на `SAFE`. Это проверка переноса
модели и логики, а не оценка точности на целевой камере.

## Журнал и метрики

`runtime/` исключён из Git. SQLite хранит отдельные эпизоды ALARM и FAULT:
UTC-время начала/конца, длительность, причины, настройки и детекции.
В начале ALARM сохраняется JPEG с зоной и боксами. Для FAULT снимок не сохраняется,
чтобы устаревший кадр не выглядел текущим. Хранятся не более 500 событий,
старые снимки удаляются вместе с событиями; панель показывает последние 100.
После аварийного перезапуска незакрытый эпизод получает причину `process interrupted`,
его длительность остаётся неизвестной.

CSV содержит последние 1000 результатов, принятых supervisor. Это скользящий
буфер для диагностики, а не запись всего длительного эксперимента.

- `inference_ms`: время вызова `RKNNLite.inference`, без preprocessing и NMS.
- `frame_to_result_ms`: от получения кадра OpenCV до завершения постобработки.
  Это не задержка от экспозиции сенсора; внутренние буферы камеры могут добавить время.
- FPS: частота новых результатов, принятых supervisor за последние две секунды.
- p95: 95-й процентиль `frame_to_result_ms` по последним 1000 результатам.
- `confirmation_seconds` в журнале: от получения первого кадра PENDING до программного
  перехода в ALARM; задержка физического буззера/UART отдельно не измерена.

Для исследования на плате дополнительно измерьте ложные тревоги за час,
долю пропущенных эпизодов, температуру, устойчивость за длительный прогон и
мощность внешним измерителем. Демо-метрики всегда помечены `mode=demo`.

## Архитектура и проверки

```text
capture thread → latest-frame slot → inference thread (NPU core 0)
                                            ↓ latest result
                     supervisor → state machine → LED/UART
                         ↓ JPEG, SQLite, metrics
                     HTTP server → local browser
```

Очередь кадров не накапливается. Веб-клиенты получают готовый JPEG, а не запускают
новый инференс. Обработка выходов соответствует экспортированному тензору
`1×6×8400`: RGB uint8 NHWC, letterbox 640, нормализация внутри RKNN,
class-aware NMS и восстановление координат. Вход INT8/split не поддерживается.

```bash
python -m unittest discover -s tests -v
```

Автотесты проверяют NMS/координаты, ROI, подтверждение и гистерезис, FAULT,
устаревший поток, защиту от повторного подтверждения одного кадра, настройки,
SQLite/снимки/retention, LED/ограничение звука и HTTP API.

Локально приложение проверено на Windows/Python 3.12 в деморежиме.
На Firefly ещё нужны: совпадение постобработки с контрольными 13 кадрами,
видео целевой камеры, NPU, физические LED/UART/ESP32, полный сценарий
снятия/надевания каски и длительный тест. Автотесты не заменяют эти проверки.
