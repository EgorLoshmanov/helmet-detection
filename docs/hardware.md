## Предварительная проверка камеры

- Текущий формат `/dev/video-camera0`: NV12, 800×600.
- Узел сообщает форматы UYVY, NV16, NV61, NV21, NV12, NM21 и NM12.
- Максимальный заявленный размер: 800×600.
- Первая попытка захвата ошибочно запрашивала 1920×1080 и завершилась сообщением `VIDIOC_STREAMON returned -1 (Operation not permitted)`.
- Полученный файл `/tmp/fortniteballs-frame.nv12` имеет размер 0 байт, поэтому пункт захвата кадра пока не выполнен.
- Нужен повторный тест в разрешении 800×600 и проверка занятости `/dev/video11`.

Повторный тест на 800×600 показал:

- пользователь `firefly` имеет чтение и запись через группу `video`;
- `/dev/video11` не занят другим процессом;
- `VIDIOC_REQBUFS`, `VIDIOC_QUERYBUF`, `VIDIOC_QBUF` и настройка NV12 800×600 проходят успешно;
- `VIDIOC_STREAMON` стабильно завершается `Operation not permitted`;
- файлы кадров остаются пустыми.

Таким образом, проблема находится не в разрешении или Unix-правах на `/dev/video11`. Нужно проверить media graph, физический сенсор, kernel log и службу RKAIQ.

Проверка media graph показала:

- `/dev/media0` содержит RKCIF, MIPI CSI2 и DPHY;
- `/dev/media1` содержит RKISP и его выходные узлы;
- в графе отсутствует физический sensor entity с именем вроде `imx*` или `ov*`;
- `v4l2-ctl --list-devices` сообщает `Failed to open /dev/video0: No such device`;
- `rkaiq_3A.service` загружена, но находится в состоянии `inactive (dead)`.

Предварительный вывод: виртуальный видеотракт создан, но физический CSI-сенсор не зарегистрирован. Возможные причины — камера не подключена, несовместимый модуль, отсутствующий драйвер или неверная DTS-конфигурация. Для подтверждения нужен kernel log.

Kernel log подтвердил причину:

```text
rkcif_update_sensor_info: get remote terminal sensor failed
update sensor info failed -19
rkisp0-vir0: check rkisp_mainpath link or isp input
```

Код `-19` соответствует `ENODEV`: драйвер не обнаруживает физический сенсор на входе MIPI/RKCIF. Захват кадра и непрерывного потока остаются заблокированы до физической проверки CSI-камеры, исправления DTS/драйвера либо подключения USB UVC-камеры.

## Предварительный тест NPU

- Драйвер и RKNN Runtime установлены.
- `/dev/dri/renderD128` и `/dev/dri/renderD129` принадлежат группе `render`.
- Пользователь `firefly` пока не входит в группу `render`, ACL выдан только пользователю `lightdm`.
- Первый Python-тест остановился до загрузки RKNN-модели: активный `/home/firefly/miniconda3/bin/python3` не содержит модуля NumPy.
- Требуется найти готовое Python-окружение или C-демо, после чего отдельно проверить доступ к NPU.

Найдены Conda-окружения:

- `base`;
- `24942` — разрешённое окружение команды;
- `venv`.

Системный `/usr/bin/python3` содержит NumPy, но не содержит `rknnlite`. В `base` отсутствуют оба пакета. Состав `24942` ещё проверяется. Также найдено системное C-демо `/usr/bin/rknn_common_test`.

Окружение `24942` проверено:

- Python 3.10.21;
- NumPy установлен;
- `rknnlite` установлен;
- дополнительная установка пакетов для базового NPU-теста не требуется.

Синтаксис системного демо:

```text
rknn_common_test model_path input_path [loop_count]
```

Первый запуск системного демо подтвердил загрузку RKNN Runtime и модели как от `firefly`, так и через `sudo`:

- RKNN Runtime: `2.3.2`;
- драйвер RKNPU: `0.9.8`;
- модель: `/usr/share/model/RK3588/mobilenet_v1.rknn`;
- вход модели: `1 × 224 × 224 × 3`, `NHWC`, `INT8`;
- выход модели: `1001` значение, `FP16`.

Инференс в этом запуске не выполнялся: `/usr/bin/rknn_common_test` передаёт вход в `cv::imread`, поэтому сырой файл `.bin` был отклонён как изображение. Следующий тест выполняется с корректным PPM-файлом. Сам факт успешного чтения метаданных модели подтверждает, что RKNN Runtime загружает модель от обычного пользователя `firefly`; предварительное предположение о блокировке из-за отсутствия группы `render` пока не подтвердилось.

Повторный запуск с корректным изображением `/tmp/fortniteballs-npu-test.ppm` успешно выполнил три инференса на NPU от обычного пользователя `firefly`:

| Проход | Время | Расчётный FPS |
|---:|---:|---:|
| 1 | 3.07 мс | 325.84 |
| 2 | 2.96 мс | 337.61 |
| 3 | 2.93 мс | 340.83 |

Код возврата `rknn_common_test`: `0`. Были получены значения Top-5, следовательно, прошли загрузка модели, передача входа, аппаратный инференс и чтение выхода. Добавлять `firefly` в группу `render` для текущей конфигурации не требуется. Эти значения характеризуют только системную MobileNet и не являются ожидаемой производительностью будущей YOLO-модели.
