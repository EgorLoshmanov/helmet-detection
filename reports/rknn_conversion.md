# RKNN-конвертация и проверка на Firefly

Дата: 28 сентября 2026 года. Исходная модель: `models/helmet_detector.onnx`, SHA-256 `ed17d0c71fa5f351c4e9b10e6318e84e0902c08763b82e64d659a4f5b92b04ba`. RKNN-Toolkit2 `2.3.2`, Runtime `2.3.2`, драйвер RKNPU `0.9.8`, платформа `rk3588`. Конвертация выполнялась в Docker Linux ARM64 с Python 3.10, инференс — через `RKNNLite` в окружении `24942` на Firefly. Вход: RGB `uint8`, NHWC, letterbox `640×640`, `mean=0`, `std=255` в конфигурации RKNN.

| Вариант | SHA-256 RKNN | Детекции ONNX / RKNN | Совпало | Медиана вызова RKNNLite.inference |
|---|---|---:|---:|---:|
| FP16 | `72c5fdf379d0f9dced422e27689cb4a344b12b32c84bc188f91a8ce9fa271747` | 175 / 175 | 174 | 40.98 мс |
| INT8, объединённый выход | `c99b37996dee91d4d24478dff536021621e34e632a8c9b4a4310d16a34552046` | 175 / 0 | 0 | 19.41 мс |
| INT8, раздельные выходы | `ccfb318ed3b20923671bc9fa098e1940ae10d972ce41c399b132744259cbe78c` | 175 / 459 | 9 по строгому допуску | 18.97 мс |
| Смешанная INT8/FP16 | `606eba7ca2cb741ddddc52b433c0437fa6f439d82a2feb7a8276d58d38d8a016` | 175 / 214 | 42 по строгому допуску | 18.84 мс |

Сравнение выполнено на одинаковых 13 изображениях тестовой части датасета v1 с одинаковыми letterbox, порогами confidence `0.25` и NMS IoU `0.7`. Это **проверка переноса модели**, а не независимая оценка точности на целевой камере. Подробные отчёты: `rknn_fp16_comparison.json`, `rknn_int8_comparison.json`, `rknn_int8_split_comparison.json` и `rknn_hybrid_comparison.json`. Измерено время вызова `RKNNLite.inference` на одном ядре NPU после прогрева, без чтения камеры и постобработки. Это не end-to-end FPS и не чистое аппаратное время NPU.

FP16 близок к ONNX, но строгий критерий выполнен для 12 из 13 кадров: в многолюдном кадре по одной граничной детекции на каждой стороне не нашлось пары. FP16 пригоден для следующего экспериментального шага, но требуется проверка на независимых данных и целевой камере.

У исходного ONNX один выход `1×6×8400`: координаты имеют значения в сотнях пикселей, вероятности классов лежат в `0…1`. При INT8-квантизации общего выхода все вероятности округлились до нуля. `export/split_onnx_outputs.py` выводит уже существующие до последнего `Concat` тензоры боксов `1×4×8400` и классов `1×2×8400`. Это не меняет вычисления: после обратного объединения ONNX Runtime выдаёт побитово одинаковый результат. Однако и разделённый INT8 не прошёл сравнение: координаты стали грубее, после NMS возникли многочисленные лишние детекции. Смешанная квантизация Toolkit2 с FP16-координатной частью после DFL уменьшила число лишних детекций с 459 до 214, но строгий критерий прошли лишь 3 из 13 кадров. Ни один из INT8-вариантов **не допускается к сигнализации**.

Калибровка подготовлена из 96 изображений обучающей части v1: по 32 кадра с каской, без каски и обоими классами. Выборка фиксирована seed `20260919`, перечень и SHA-256 — в `rknn_calibration.json`. Кадры с целевой камеры отсутствуют, поэтому набор временный. При сборке Toolkit сообщил о выбросе веса `model.0.conv.weight`; сообщений о неподдерживаемых операциях в логе не было. Статическое RKNN на плате также выдаёт предупреждение о запросе dynamic range; запуск модели при этом завершается успешно.

Следующий шаг для INT8: исследовать причины остаточных ошибок смешанного варианта, возможно сохранить в FP16 больший участок детекционной головы, затем снова прогнать эти же 13 кадров и независимую тестовую выборку. Пока для приложения использовать FP16 и не подключать исполнительный сигнал по непроверенному INT8.
